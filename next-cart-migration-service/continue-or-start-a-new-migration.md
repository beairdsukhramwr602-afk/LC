# Continue or Start a New Migration

After a migration has already been performed under the purchased Next-Cart migration service license, customers may need another migration action for the same migration path. The source store may keep receiving new orders, customers, products, or content while the target store is being prepared. The customer may also want to adjust configuration before another execution or start a fresh migration result for the selected path.

Next-Cart supports these needs through available migration actions inside the purchased service license. The right choice depends on what the customer wants to achieve: add later source-store data, continue with adjusted settings, or create a new migrated result for the same migration path.

### When These Migration Actions Matter <a href="#when-these-migration-actions-matter" id="when-these-migration-actions-matter"></a>

Later migration actions become useful after the customer has already performed migration activity under the purchased service license.

They are commonly relevant when:

* the source store remains active while the target store is being reviewed;
* new orders, customers, products, or Blog Posts appear after an earlier migration;
* the customer wants another execution using the same settings as before;
* the customer wants to change configuration before continuing migration activity;
* the previous target-store result should be replaced by a new migration result;
* validation shows that the next action should be planned before launch or further review.

These actions should be chosen based on the customer’s business goal, not only on whether another run is possible. A useful choice starts with a simple question: should the next action add to the previous migration result, continue with adjusted settings, or create a fresh result?

### Available Migration Actions After a Completed Migration <a href="#available-migration-actions-after-a-completed-migration" id="available-migration-actions-after-a-completed-migration"></a>

After performing a migration with the purchased migration service license, customers can access the license again and continue working with the same migration path. Depending on migration history and service availability, the customer may be able to choose one of these actions:

| Migration action                                        | Best used when                                                                                                  | Practical outcome                                                                                                 |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Continue the Migration with the last used configuration | The previous configuration is still suitable and the customer wants to continue migration activity efficiently. | The next execution follows the last used configuration.                                                           |
| Continue the Migration with a new configuration         | The customer wants to continue migration activity but adjust settings before execution.                         | The customer can review or change configuration before continuing.                                                |
| Perform a new migration                                 | The customer wants a fresh migration result for the same migration path.                                        | The migration is performed again for the selected scope and may replace the earlier migrated target-store result. |

The selected action should match the intended target-store outcome. Continuing a migration is usually about adding or updating migration activity based on earlier work. Performing a new migration is better suited when the customer wants a fresh result rather than continuing from the previous migrated result.

### Continue the Migration with the Last Used Configuration <a href="#continue-the-migration-with-the-last-used-configuration" id="continue-the-migration-with-the-last-used-configuration"></a>

Continue the Migration with the last used configuration is useful when the earlier migration settings still match the customer’s goal.

This action can help when the source store has changed after earlier migration activity and the customer wants the target store to receive later data without rebuilding the configuration decision from the beginning. It is especially useful when the earlier configuration was already reviewed, the target-store result was acceptable, and the customer expects the next execution to follow the same setup.

Typical reasons to choose this action include:

* new orders were created in the source store after the previous migration;
* new customers registered before launch;
* new products or Blog Posts were added;
* the previous configuration remains suitable for the target-store result;
* the customer wants a faster continuation path based on already reviewed settings.

The main advantage is efficiency. The customer can continue migration activity using the last used configuration instead of repeating configuration decisions that are already suitable.

### Continue the Migration with a New Configuration <a href="#continue-the-migration-with-a-new-configuration" id="continue-the-migration-with-a-new-configuration"></a>

Continue the Migration with a new configuration is useful when the customer wants to continue migration activity but needs to adjust settings first.

This action fits situations where the earlier migration provided useful evidence, but the next execution should use a revised configuration. The customer may want to adjust mapping, filtering, selected options, Add-on settings, or other configuration choices before continuing.

Typical reasons to choose this action include:

* Demo Migration or validation revealed that some settings should be adjusted;
* the customer wants to apply different filtering or mapping decisions;
* the target-store result needs a configuration change before another execution;
* Add-on behavior needs to be aligned with the next migration activity;
* the customer wants more control before continuing from earlier migration work.

The main advantage is flexibility. The customer can continue migration activity while making configuration choices that better fit the intended target-store result.

### Perform a New Migration <a href="#perform-a-new-migration" id="perform-a-new-migration"></a>

Perform a new migration is useful when the customer wants a fresh migration result for the same migration path instead of continuing from the previous migrated result.

This action may be appropriate when the earlier result should no longer be used, when configuration or scope needs a clean restart, or when the target store should reflect a newly selected migration setup.

Typical reasons to choose this action include:

* the customer wants to replace the earlier migrated target-store result;
* the previous configuration no longer matches the intended outcome;
* the migration scope needs to be reconsidered from the beginning;
* the target store was used for testing and the customer now wants a cleaner result;
* validation shows that the better path is a new migration result rather than continuation.

The main advantage is a cleaner reset of the migration result for the selected path. Because this action can affect previously migrated target-store data, the customer should confirm the expected target-store outcome before execution.

### How Entity Points Apply <a href="#how-entity-points-apply" id="how-entity-points-apply"></a>

Entity Points are tied to counted records and their recorded migration status under the purchased service license.

If a later migration action migrates new Product, Customer, Order, or Blog Posts records for the first time, the corresponding Entity Points are used. Counted records already recorded through the service license do not consume Entity Points again when migrated again, including when the customer performs a new migration.

This allows customers to plan later migration activity around real counted-data needs. New counted records require available capacity, while already recorded counted records are not counted again simply because another migration action is performed.

### How Service Responsibility Works <a href="#how-service-responsibility-works" id="how-service-responsibility-works"></a>

Customers of any service model can access and perform available migration actions manually if they choose.

Responsibility depends on the selected service model and agreed scope:

| Service model                        | Who performs migration actions                                                                                                                                           | Customer responsibility                                       |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| Standard Service                     | The customer performs migration actions.                                                                                                                                 | The customer verifies the final result and migration outcome. |
| Custom Service without Expert Handle | The customer performs migration actions.                                                                                                                                 | The customer verifies the final result and migration outcome. |
| Managed Service                      | Next-Cart performs migration actions based on the customer’s request and agreed service scope. The customer can still perform available actions manually if they choose. | The customer verifies the final result and migration outcome. |
| Custom Service with Expert Handle    | Next-Cart performs migration actions based on the customer’s request and agreed custom scope. The customer can still perform available actions manually if they choose.  | The customer verifies the final result and migration outcome. |

The service model affects who performs or coordinates the action. It does not remove the customer’s responsibility to confirm that the target-store result matches the intended migration outcome.

### What to Check Before Choosing an Action <a href="#what-to-check-before-choosing-an-action" id="what-to-check-before-choosing-an-action"></a>

Before choosing how to continue, customers should clarify what they want the next migration action to accomplish.

Useful questions include:

* Should the next action add later source-store data to the target store?
* Is the last used configuration still suitable?
* Should the configuration be reviewed or changed before another execution?
* Should the earlier target-store result be replaced by a fresh migration result?
* Is there enough Entity Points capacity for newly migrated counted records?
* Are Add-ons needed for filtering, mapping, or data configuration?
* Does the requirement involve custom fields, app data, extension data, plugin data, Custom Platform handling, or custom migration logic?
* Who should perform the action under the selected service model?
* What target-store result must be verified afterward?

These questions help prevent customers from choosing an action only because it is available. The safest action is the one that matches the intended business result.

### What to Verify After the Migration Action <a href="#what-to-verify-after-the-migration-action" id="what-to-verify-after-the-migration-action"></a>

After the selected action is performed, customers should review the target-store result against the expected outcome.

The review should focus on the purpose of the action:

| Action used                               | Validation focus                                                                                                        |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Continue with the last used configuration | Confirm that later source-store data appears correctly and that the previous target-store result remains usable.        |
| Continue with a new configuration         | Confirm that the revised configuration produced the expected target-store result.                                       |
| Perform a new migration                   | Confirm that the target store reflects the intended new result and does not rely on unwanted previous migration output. |

Validation should include the records most important to the business: products, customers, orders, Blog Posts, CMS Pages, reviews, coupons, URLs, mappings, filtered records, Add-on-affected records, and Custom Service-related data where relevant.

A migration action is successful only when the customer can confirm that the target store supports the intended next business step.

### Common Mistakes to Avoid <a href="#common-mistakes-to-avoid" id="common-mistakes-to-avoid"></a>

#### Choosing continuation when the result should be replaced <a href="#choosing-continuation-when-the-result-should-be-replaced" id="choosing-continuation-when-the-result-should-be-replaced"></a>

Continuation is useful when the customer wants to build on earlier migration activity. If the earlier target-store result should no longer be used, performing a new migration may be more suitable.

#### Starting a new migration when configuration adjustment is enough <a href="#starting-a-new-migration-when-configuration-adjustment-is-enough" id="starting-a-new-migration-when-configuration-adjustment-is-enough"></a>

A new migration may be unnecessary when the customer only needs to continue with revised settings. If the earlier result is still useful, continuing with a new configuration may provide a more focused path.

#### Ignoring later source-store changes <a href="#ignoring-later-source-store-changes" id="ignoring-later-source-store-changes"></a>

If the source store remains active, new records may appear after earlier migration activity. Customers should consider whether those records need to be included before launch or before the target store is used for business operations.

#### Forgetting to verify the result <a href="#forgetting-to-verify-the-result" id="forgetting-to-verify-the-result"></a>

The selected action does not replace validation. Customers still need to confirm that the target store contains the expected data and supports the intended business outcome.

### Conclusion <a href="#conclusion" id="conclusion"></a>

Continue or Start a New Migration helps customers choose the right next action after migration activity has already taken place under the purchased service license. Continuing with the last used configuration supports efficiency when the previous setup is still suitable. Continuing with a new configuration supports flexibility when settings need adjustment. Performing a new migration supports a fresh target-store result when the earlier migrated result should be replaced.

The best choice depends on the customer’s goal, source-store changes, configuration needs, Entity Points capacity for newly migrated counted records, service responsibility, and validation expectations. If the right action is unclear, Live Chat can help review whether the next step should be continuation, configuration adjustment, a new migration, Add-ons, Custom Service review, or expert-handled execution.

### FAQs <a href="#faqs" id="faqs"></a>

**When can customers continue or start a new migration?**

After performing a migration with the purchased migration service license, customers can access available migration actions for the same migration path, depending on migration history and service availability.

**What is the difference between continuing with the last used configuration and continuing with a new configuration?**

Continuing with the last used configuration uses the previous settings. Continuing with a new configuration allows the customer to review or adjust settings before another execution.

**When should a customer perform a new migration?**

A customer should perform a new migration when the goal is to create a fresh migration result for the same migration path rather than continue from the previous migrated result.

**Does continuing a migration consume Entity Points?**

New Product, Customer, Order, and Blog Posts records consume Entity Points when they are migrated for the first time. Counted records already recorded through the service license do not consume Entity Points again when migrated again.

**Does performing a new migration consume Entity Points again for already recorded records?**

No. Counted records already recorded through the service license do not consume Entity Points again when migrated again, including when a new migration is performed.

**Can customers perform these actions manually?**

Yes. Customers of any service model can access and perform available migration actions manually if they choose.

**Who performs these actions under Managed Service or Custom Service with Expert Handle?**

Next-Cart performs migration actions based on the customer’s request and agreed service scope. The customer can still perform available actions manually if they choose.

**What should customers check after using one of these actions?**

Customers should verify that the target store contains the expected data, reflects the intended configuration or migration result, and is suitable for the next business step.
